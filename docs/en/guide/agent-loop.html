Agent loop

Chat, code sessions, the kanban board and workflows all share one kernel: HetuAgentRunner.RunAsync. It composes Microsoft Agent Framework's ChatClientAgent, FunctionInvokingChatClient and ToolApprovalAgent directly, and only handles product events, history-provider integration and result aggregation.

Order of a single run

  1. Resolve the model: a ModelId on the request creates that provider, otherwise the default chat model is used; if neither exists the run throws instead of silently substituting another model.
  2. Load tools: built-in / session tools first, then tools/list from the MCP servers bound to the session; the merged set refreshes the tool schemas and system prompt.
  3. Enter the loop (15 iterations per segment by default): each iteration first drains steering into context. Chat and code sessions load history from the database into PreloadedChatHistoryProvider; other entries use InMemoryChatHistoryProvider. History is compressed by HetuChatReducer before use, then the model is called. When a single request exceeds 40% of the context window, AgentContextChatClient runs long text through the compression pipeline once more; above 80% it stops tool calls and wraps up. RAG / steering AIContextProviders live in the chat-client pipeline and run before every model call; AgentSkillsProvider runs at agent level so it can inject skill tools.
  4. Handle output: prose and thinking stream out as events; tool calls go to the caller's decider, which either executes them or requests approval.
  5. Feed results back: tool results enter the context and are pushed to the UI; per-iteration prose, thinking, tools and usage accumulate into the run result.
  6. Finish: the run ends when no further tool calls arrive. At the per-segment iteration cap MAF automatically performs one final request without tools. If the segment made real progress and MaxContinuations is not exhausted, the runner emits an iteration_continue notice and automatically starts the next segment; only after continuations are used up does it mark iteration_limit. The caller persists messages, records usage and appends done.

Mid-run steering

  • Injected at a fixed point — the start of each iteration — so it never interrupts a tool chain halfway and contradicts the context.
  • The injected text carries a fixed prefix (【运行中引导，请立即结合它调整当前工作】) so the model can tell it is a mid-run redirection.
  • Clicking "steer" while streaming queues the instruction in AgentSteeringHub; the next iteration picks it up. A pending plan/question wait is resolved first so the new instruction can take effect immediately.
  • Queue vs steer: a queued message is sent after the current turn; a steer changes the running turn immediately.

History compression boundaries

BehaviourImplementation
ScopeThe current user message is sent directly as this turn's input by default; InMemoryChatHistoryProvider only loads and compresses earlier messages. If a single request exceeds 40% of the context window (Anchor), AgentContextChatClient runs long text through the compression pipeline once more (SHA-256 caching keeps the same slice stable); above 80% it stops tool calls and wraps up. Tool output produced by the active turn has a separate deterministic budget: old results are compacted while ToolCallId linkage and recent results are preserved
DeduplicationCompressionPipelineService.PrepareForContextAsync caches compressed content by SHA-256, so the same slice is not recompressed across iterations
MethodLong messages go through the compression pipeline first; when history reaches 80% of the context window, older messages are summarized by the current model, the most recent 6 are kept, then the remainder is compressed
Cost visibilityThe first iteration estimates system prompt and tool schema character cost and logs it, separating "heavy prompt" from "long history"

Session persistence and long-term history

  • Chat / code sessions serialize the MAF AgentSession into AppSettings (key prefix agent-session:) and restore it across requests; message history still comes from the database.
  • Setting EnableHistoryMemory=true enables ChatHistoryMemoryProvider; HetuChatHistoryVectorStore stores messages and embeddings in local SQLite / PostgreSQL. SQLite uses sqlite-vec MATCH, PostgreSQL uses pgvector <=>; when the extension is unavailable it falls back to in-memory cosine similarity.
  • UsePerServiceCallHistoryPersistence=true makes MAF load/persist history around every inner model call; do not enable it together with EnableHistoryMemory.
  • HistoryMemoryRetentionDays is enforced by a daily cleanup worker that removes expired vectors and agent-session: snapshots; adjust it under Settings → Memory.
  • Local projects use AgentFileSkillsSource for .github/skills; skill scripts run through pwsh / bash / python / node after approval (5-minute timeout). SSH projects keep work_skill as a remote-compatible fallback.

Tool loading and MCP

  • MCP servers that are missing or disabled are skipped with a warning; a single server failing to load logs an error and continues the turn instead of breaking it.
  • Both stdio and HTTP/SSE transports are supported; loaded McpClientTool instances are passed directly to MAF as AIFunctions and merged with built-ins, with built-ins winning name conflicts.
  • MCP tools are never persisted; server configuration lives in settings.

Failure and degradation

  • Model unavailable: throws, and the UI receives an error frame — no silent model substitution.
  • A single MCP server fails: that server is skipped, other tools keep working.
  • Cancellation: OperationCanceledException is not swallowed, and parsed tools that have not started never execute after cancellation; the caller decides whether it means "cancelled" or "requeue".
  • Tool protocol errors: textual <tool_call> markup is parsed across deltas and converted to MAF FunctionCallContent. Truncated calls, malformed arguments and batches above the per-turn limit are never executed. Unrecognized text is preserved verbatim.
  • Provider errors: transient errors and empty turns are retried a bounded number of times (ProviderMaxRetries); once prose has been streamed to the UI, no retry happens to avoid duplicate output.
  • Spinning / context exhaustion: the same call failing twice is skipped on the third attempt; two consecutive iterations with only duplicate calls count as stalled. Stalled or over the hard context cap, tool calls stop, a notice is emitted and the model wraps up.
  • No interaction channel: unattended entries such as workflow agent/tool nodes use InteractiveToolsSupported = false; Ask, ask_question and plan return a clear error instead of waiting for a timeout.
  • Compression failure: the pipeline degrades internally only (missing provider or a non-shorter result returns the original text).

Non-obvious but important

  • The iteration and tool limits are guard rails, not business rules: the former stops loops, the latter is enforced through the prompt so the model keeps judgement.
  • Steering is injected only at iteration boundaries; several clicks within one iteration are drained as one instruction.
  • Chat and code sessions differ in their permission decider and tool set, not in the kernel (code sessions bring work_* tools and a workspace scope).
  • Kanban and workflows reuse the same kernel, swapping the event outlet for run-step / node-event recording.
  • Identical read-only calls within one turn reuse the previous result; the same call failing twice in a row is skipped the third time to stop loops burning the iteration budget.
  • Tool calls run serially by default (AllowConcurrentInvocation = false) so file-change order, checkpoints and approval events stay consistent; remote SSH projects also stay sequential to avoid sharing a runner.
  • MCP clients are pooled per connection config and handshake once per process; SSE content/thinking deltas are coalesced to ~60ms or 512 characters.
  • The work_task sub-agent is exposed through AIAgent.AsAIFunction (agent-as-tool): read-only tool whitelist with a 12-iteration / 3-minute cap, while SubAgentSink still turns its events into subagent frames.
  • The agent pipeline is wrapped with AIAgentBuilder.UseOpenTelemetry, keeping MAF-native tracing; non-agent text tasks use ChatJsonWithUsageAsync<T> / ChatResponseFormatJson for structured output.

Debugging hints

  • Start with the [AgentLoop] and [Compression] log lines: the first shows iteration counts and tool loading, the second shows before/after sizes of history compression.
  • Suspect compression is changing behaviour? Turn CompressHistory off and reproduce.
  • Tool unexpectedly unavailable: check whether the MCP server is disabled, whether its connection config can be parsed (stdio and HTTP/SSE are supported), and whether the tool is denied by the permission mode or a project rule.
